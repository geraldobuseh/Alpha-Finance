# PQL-019: strategy responsibility boundary

Hypothesis: a small proposal-only interface lets strategies vary independently of
execution policy without granting access to live portfolio mutations.
Problem: there is no common strategy contract. Learning objective: separate
observation, decisions and proposals from authorization, fills and accounting.
Generation target: Strategy interface, PortfolioState name for the existing detached
snapshot, synthetic contract tests. Resolution signal: exact methods compile,
proposals do not mutate the portfolio, and separately executed proposals can fill
or reject through the existing broker.

## Contract

Include `strategy/strategy.hpp`; existing domain include paths expose this
header-only interface. It declares:

```cpp
virtual std::vector<Order> generateOrders(
    const MarketState& market, const PortfolioState& portfolio) = 0;
virtual std::string name() const = 0;
virtual ~Strategy() = default;
```

PortfolioState aliases PortfolioSnapshot because both describe the same detached,
owning observation value. It is not a mutable Portfolio, and a live Portfolio cannot
implicitly bind to this input. Positions and transaction history are const-access
values with no trade-application API. No duplicated accounting model is introduced.

Inputs are borrowed only for the call; implementations must not retain their
references. Returned orders and name strings own their data. Empty order output
means no action. generateOrders is nonconst to permit eventual internal strategy
state; this does not grant financial mutation authority.

## Responsibilities

- Strategy observes supplied state, decides and proposes valid typed Orders.
- Trusted orchestration supplies inputs and submits proposals to a Broker.
- Broker validates and executes using current cash, holdings and trading costs.
- Portfolio records accepted transaction consequences through its atomic ledger.

A proposal is not a fill, reservation or spending authorization. A strategy can
propose a one-share buy at a $100 quote with $100 cash; a broker charging $1 must
reject it without charging fees or changing holdings/history. Test fixtures verify
this independently of the strategy's decision logic.

Never inject a mutable Portfolio, Broker, transaction writer or mutation callback
into a strategy. C++ interfaces constrain the provided capabilities, not arbitrary
implementation behavior; orchestration must preserve this ownership rule.

## Scope and limits

No production strategy, scheduler, order-ID allocator, database schema or historical
data API is added. Fixture IDs are explicit test inputs. Future orchestration must
provide an ID policy and define batch ordering and partial batch execution behavior.

MarketState currently contains one synthetic quote. Callers must align both market
inputs and portfolio history with the allowed decision horizon; a detached const
snapshot can still contain future information. This ticket does not establish
backtest availability gating, strategy quality or benchmark outperformance.

Tests check exact signatures and virtual destruction, absence of mutation APIs,
no-action output, owned proposals, snapshot isolation and separate successful or
rejected execution. Evidence is recorded in `.codex/reviews/PQL-019/`.
